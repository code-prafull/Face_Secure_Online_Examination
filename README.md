# Face Secure — Online Examination & AI-Based Proctoring System

A full-stack examination platform where **invigilators conduct exams** and every candidate
session is proctored **in real time, right in the browser** — extra faces, missing face,
mobile-phone detection, identity lock (unknown face), tab-switch / copy-paste / fullscreen
guards — with **instant on-screen interrupts** for the candidate and **live alerts** for the
invigilator. No external AI API key is required: detection runs on-device and session
summaries are generated by a deterministic, local rule-based algorithm.

| Layer     | Stack                                                                 |
|-----------|-----------------------------------------------------------------------|
| Frontend  | React 19 + Vite, Tailwind CSS v4, React Router 7, Axios, Recharts, sonner, react-icons |
| Backend   | Node.js + Express 5, MongoDB (Mongoose), JWT (HttpOnly cookies), jsPDF |
| ML (client) | `@vladmandic/face-api` (identity lock), `@tensorflow-models/coco-ssd` (mobile/object detection) |

## Features

### Candidate
- Register / login (JWT in **HttpOnly cookie**, `withCredentials`), profile management
- Exam lobby → **3-step entry**: instructions + consent → **face verification (identity lock)** → proctored exam
- Interview-style exam flow: MCQ + coding questions, countdown timer, fullscreen enforcement
- **Instant on-screen interrupts** the moment anything suspicious is detected (with 15s cooldown):
  multiple faces · no face · mobile phone · **unknown face (identity mismatch)**
- Screen guards: tab/window switch, copy/paste/right-click, fullscreen exit — all recorded
- Automatic MCQ scoring, own results + suspicion/violation history, exam history
- Forgot → reset password (dev-mode link when no SMTP is configured)

### Invigilator (teacher)
- Dashboard with **real backend analytics** (students, exams, violations, camera events)
- Full exam lifecycle: create (with instructions, total/passing marks, camera rules,
  **student assignment**), update, delete (cascades), quick **status control** (upcoming → active → completed)
- Question bank (MCQ + coding) per exam
- **Live monitoring** per exam: auto-refreshing per-candidate timeline merging camera
  events + screen-guard violations, suspicion risk badges, **local rule-based session summary**
- **Any invigilator can conduct any exam** (no creator-only lock) — read/grade/manage by role
- Grading view with auto-scores, manual coding review + feedback, CSV export
- **Students directory** with per-student exam history modal
- **Reports hub**: academic + proctoring report, cross-exam roll-up, **server-rendered PDF export**

### Admin
- Same invigilator capabilities (routes shared, `/admin` → invigilator dashboard)

## Quick start

### Prerequisites
- Node.js 18+
- MongoDB running locally (default `mongodb://127.0.0.1:27017/smart-exam-proctoring`)
- A modern browser with webcam support (Chrome/Edge)

### 1) Backend

```bash
cd backend
npm install
copy .env.example .env      # Windows (or: cp .env.example .env)
# edit .env → MONGO_URI, JWT_SECRET at minimum
npm start                   # → http://localhost:5000
```

### 2) Frontend

```bash
cd frontend
npm install
npm run dev                 # → http://localhost:5173
```

The API base URL defaults to `http://localhost:5000/api` and can be overridden with
`frontend/.env` → `VITE_API_URL`. CORS is restricted to `CLIENT_URL` (default `http://localhost:5173`).

### Environment variables (`backend/.env`)

| Key            | Example                                            | Required |
|----------------|----------------------------------------------------|----------|
| `PORT`         | `5000`                                             | yes |
| `NODE_ENV`     | `development`                                      | yes |
| `MONGO_URI`    | `mongodb://127.0.0.1:27017/smart-exam-proctoring`  | yes |
| `JWT_SECRET`   | long random string                                 | yes |
| `CLIENT_URL`   | `http://localhost:5173`                            | yes |
| `GEMINI_API_KEY` | *(optional — summaries run locally without it)*  | no |

## Deploying to Render

The repo ships with a **`render.yaml`** Blueprint and a root `package.json` — one web
service serves **both** the Express API and the built React SPA from the **same origin**
(no CORS/cookie configuration needed: the build inlines `VITE_API_URL=/api`, so axios
calls hit the service's own `/api` routes, and `backend/src/app.js` serves
`frontend/dist` with an SPA fallback for client routes).

### One-time: MongoDB Atlas
1. Create a free [MongoDB Atlas](https://www.mongodb.com/atlas) cluster + database user.
2. **Network Access → IP Address → Allow Access from Anywhere** (`0.0.0.0/0`) —
   Render's egress IPs are dynamic.
3. Copy the connection string: `mongodb+srv://user:pass@…/face-secure`.

### Deploy A — Blueprint (recommended)
1. Push this repo to GitHub.
2. Render dashboard → **New + → Blueprint** → select the repo (Render reads `render.yaml`).
3. When prompted, paste **`MONGO_URI`** (Atlas string) — `JWT_SECRET` is generated for you.
4. Deploy → site at `https://<service-name>.onrender.com`.
5. If you **rename** the service, update the `CLIENT_URL` env var to the final URL.

### Deploy B — manual Web Service
| Setting         | Value |
|-----------------|-------|
| Root directory  | *(leave empty — repo root)* |
| Runtime         | Node |
| Build Command   | `npm run build` |
| Start Command   | `npm start` |
| Env vars        | `NODE_ENV=production` · `MONGO_URI=<Atlas>` · `JWT_SECRET=<random>` · `CLIENT_URL=https://<your-app>.onrender.com` · `VITE_API_URL=/api` |

### Alternative — split hosting (static SPA + separate API)
- Frontend as a **Render Static Site** (build `npm run build`, publish `dist`) and the
  backend as a Web Service.
- Set the static site's env `VITE_API_URL=https://<api-host>/api` **at build time**
  (overrides `frontend/.env.production`), and on the backend set
  `CLIENT_URL=https://<frontend-url>` (+ optionally `ALLOWED_ORIGINS=…` for more origins).

### Notes
- Free web services **spin down** after ~15 min idle → the first request after idle
  takes ~30–60 s to wake up.
- `frontend/dist` is gitignored and built fresh on every Render deploy.
- Never put secrets in `VITE_*` variables — they are inlined into the public JS bundle.

## How the proctoring works

```
candidate's browser                         backend                      invigilator's browser
─────────────────────                       ─────────                    ─────────────────────
face-api  → identity lock (reference
            descriptor, euclidean ≤ 0.55)
coco-ssd  → mobile-phone / object check
screen    → tab switch, copy/paste,
            fullscreen exit
        │
        ├─ violation/event ──────────────▶  POST /api/violations
        │                                   POST /api/events  ──────▶  Live monitor (5s refresh)
        │                                          │                    merged timeline,
        │                                   SuspicionScore               risk badges,
        │                                   updated server-side          session summary
        └─ INTERRUPT overlay shown instantly
           on the exam screen (15s cooldown)
```

- **Identity lock** — a reference descriptor is captured once at exam start; every cycle the
  live descriptor is compared on-device. A mismatch raises an `UNKNOWN_FACE` violation
  instantly (candidate interrupted + invigilator alerted).
- **Descriptors only, never images** — face photos are never uploaded. The backend additionally
  exposes `POST /api/face/verify` (two 128-d numeric descriptors, threshold `0.55`) for
  independent server-side confirmation.
- **Session summaries** are computed locally from the stored event/violation stream —
  deterministic, explainable, **no external AI API key**.
- Events/violations are indicators for human review — they do not by themselves prove malpractice.

## Security notes

- Auth via **JWT stored in an HttpOnly cookie** (`withCredentials`); `401` responses redirect to `/login`.
- **Role-based route guards** on both sides: `candidate` / `invigilator` / `admin`.
- Exam management (update/delete/status/results/questions/submissions grading) is restricted to
  **invigilator/admin by role** — intentionally *not* creator-locked so any invigilator can
  conduct any exam; candidates are blocked by the role middleware.
- Candidates receive questions **with answers stripped**; MCQ grading happens server-side.
- Reset tokens are **SHA-256 hashed**, single-use, 30-minute TTL (Mongo TTL index).
- No face images are stored or transmitted — only 128-d numeric descriptors when explicitly verified.

## Known limitations

- **No SMTP provider** — `POST /auth/forgot-password` runs in *dev mode*: the reset link is
  returned directly in the response (clearly labelled in the UI) instead of being emailed.
- `GEMINI_API_KEY` is optional; session summaries are fully local by design.
